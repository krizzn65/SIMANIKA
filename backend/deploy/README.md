# MySQL 8.0.30 pada hosting FTP

## Konfigurasi autentikasi dan email produksi

Alamat frontend dan backend memakai satu domain: `https://himanika.wsmif.myhost.id`; API berada di `/api`. Isi `backend/.env` hosting mengikuti `production.env.example`, tetapi simpan `APP_KEY`, password database, password SMTP, dan secret Google hanya di `.env` privat. Isi `frontend/.env.production.local` dari `frontend/.env.production.example` **sebelum** menjalankan `npm run build`; unggah hasil `frontend/out/` setelah build. Jangan mengunggah `.env` frontend atau backend sebagai berkas publik.

`ADMIN_EMAIL` adalah identitas Super Admin, sedangkan `MAIL_FROM_ADDRESS` adalah alamat pengirim; keduanya tidak wajib sama. Template awal memakai `himanikamif@gmail.com` untuk keduanya. Akun Gmail membutuhkan metode autentikasi SMTP yang diizinkan Google, misalnya App Password bila akun memenuhi syarat. Simpan kredensial itu hanya di `MAIL_PASSWORD` pada `.env` hosting; jangan pakai sandi login utama. Jika hosting memblokir SMTP keluar, gunakan layanan pengiriman email yang diizinkan dan tetap verifikasi bahwa alamat pengirimnya boleh dipakai.

Email verifikasi dan reset sandi memakai template SIMANIKA berbahasa Indonesia. Saat memperbarui tampilannya melalui FTP, unggah tepat tiga berkas backend berikut ke lokasi relatif yang sama: `app/Providers/AppServiceProvider.php`, `resources/views/emails/auth-action.blade.php`, dan `resources/views/emails/auth-action-text.blade.php`. Tidak perlu mengunggah frontend atau mengubah `.env` untuk perubahan desain email ini. Jika hosting menyimpan template lama, jalankan `php artisan view:clear` dan reset OPcache melalui panel bila tersedia. Tanpa terminal, hapus hanya berkas hasil kompilasi dalam `storage/framework/views` melalui FTP, bukan foldernya. Kirim ulang email verifikasi atau minta reset sandi baru untuk melihat template terbaru; email yang sudah terkirim tidak berubah.

Jika provider hosting menyediakan layanan email sendiri, gunakan parameter resmi mereka tanpa akun Google. Pilihan pertama adalah SMTP provider: tetap `MAIL_MAILER=smtp`, lalu isi `MAIL_HOST`, `MAIL_PORT`, `MAIL_ENCRYPTION`, `MAIL_USERNAME`, dan `MAIL_PASSWORD` dari panel/provider. Untuk relay lokal tanpa autentikasi, kosongkan username/password hanya jika provider mengizinkannya. Pilihan kedua adalah pengiriman lokal melalui program sendmail: set `MAIL_MAILER=sendmail` dan `MAIL_SENDMAIL_PATH` sesuai path yang diberikan provider (default kode `/usr/sbin/sendmail -bs`); SMTP username/password tidak diperlukan untuk pilihan ini. Pastikan provider memang mengaktifkan sendmail untuk akun hosting. Pada kedua pilihan, `MAIL_FROM_ADDRESS` harus memakai alamat/domain yang diizinkan provider, misalnya mailbox domain yang dibuat di panel, sementara `ADMIN_EMAIL=himanikamif@gmail.com` dapat tetap menjadi identitas admin. Periksa bagian Email Deliverability panel untuk SPF/DKIM dan uji penerimaan di alamat luar domain.

Rilis ini memakai Laravel 12 dan PHP minimal 8.2. Jika hosting menyediakan Composer, jalankan `composer install --no-dev --optimize-autoloader` berdasarkan `composer.lock` rilis ini. Jika hanya FTP, siapkan `backend/vendor/` di komputer dengan PHP 8.2 atau versi PHP hosting yang kompatibel, lalu unggah seluruh `vendor/` bersama kode; paket Laravel 11 lama tidak boleh dicampur. Simpan salinan kode dan `vendor/` rilis sebelumnya untuk rollback.

Daftarkan `https://himanika.wsmif.myhost.id/api/auth/google/callback` persis sebagai Authorized redirect URI pada OAuth Client Google. Pastikan consent screen dan akun penguji sesuai status aplikasi. `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, dan `GOOGLE_REDIRECT_URI` harus berasal dari OAuth Client yang sama.

Pembaruan penautan akun Google memakai `app/Http/Controllers/Auth/GoogleAuthController.php` dan `app/Http/Controllers/Auth/LoginController.php`. Jika email Gmail atau Google Workspace yang terverifikasi sama dengan akun manual lama, callback menautkan `google_id` pada baris pengguna itu tanpa mengganti ID, kata sandi, role, atau data pendaftaran. Untuk alamat Google pada provider email lain, pengguna harus menyelesaikan satu login manual pada browser yang sama dalam 10 menit; sesi browser diperlukan untuk menyimpan bukti OAuth sementara. Unggah kedua controller backend tersebut dan **isi** `frontend/out/` hasil build terbaru agar pesan login mengikuti alur baru. Migrasi database baru dan perubahan `.env` tidak diperlukan bila Google OAuth sebelumnya sudah berfungsi. Bersihkan cache/OPcache hosting bila kode lama masih dijalankan. Uji akun manual Gmail yang sama, akun Google yang sudah ada, dan akun dengan email berbeda; pastikan tidak ada akun duplikat di `users`.

Web server harus meneruskan `/api/*` dan `/sanctum/csrf-cookie` ke Laravel `backend/public/index.php`, sedangkan halaman frontend diambil dari hasil static export. Jangan jadikan direktori `backend/` sebagai web root. `.htaccess` di `backend/public` hanya menangani rewrite setelah request sampai ke direktori itu; pengaturan pemetaan awal domain masih harus dilakukan pada panel hosting. Jika `index.html` hasil `frontend/out/` dan `index.php` Laravel berada di folder publik domain yang sama, pastikan `index.html` ada di folder tersebut dan letakkan `DirectoryIndex index.html index.php` di bagian atas `.htaccess` yang aktif agar `/` membuka frontend. Pertahankan aturan rewrite khusus hosting yang sudah ada; jangan menimpa seluruh `.htaccess` root dengan berkas proyek bila isinya berbeda. `GET /` harus menghasilkan HTML frontend, sedangkan `GET /api/ping` harus menghasilkan JSON `{"status":"ok"}`. Pastikan `.env`, `storage/app/private`, log, dan kode PHP di luar `public/` tidak dapat diunduh dari web. Aktifkan HTTPS untuk seluruh domain, termasuk callback Google dan tautan email.

Untuk poster OPREC, batas aplikasi tetap 5 MB. PHP hosting sering memakai `upload_max_filesize=2M`, sehingga berkas 2–5 MB ditolak sebelum mencapai validasi Laravel dan dapat menghasilkan HTTP 422. Di cPanel, buka **Software → MultiPHP INI Editor**, pilih domain `himanika.wsmif.myhost.id`, lalu simpan `upload_max_filesize=10M` dan `post_max_size=12M`. Nilai `post_max_size` harus lebih besar daripada `upload_max_filesize`. Berkas `backend/public/.user.ini` memuat pengaturan yang sama untuk PHP CGI/FastCGI, sementara `backend/public/.htaccess` memuat pengaturan untuk LSAPI. Letakkan `.user.ini` di direktori `index.php` Laravel aktif. Jika `.htaccess` pada direktori itu berisi aturan khusus hosting, tambahkan dua `php_value` di dalam `<IfModule lsapi_module>` tanpa mengganti aturan lain. Pengaturan panel tetap perlu diperiksa karena server dapat mengabaikan pengaturan pada berkas. Tunggu beberapa menit agar cache konfigurasi PHP kedaluwarsa, lalu uji unggah JPG/PNG/WebP berukuran 2–5 MB dan buka URL poster hasilnya dari browser. Pastikan `storage/app/public/oprec/posters` dapat ditulis oleh proses PHP. Jika respons 413 berasal dari web server atau WAF, periksa batas request di panel hosting; jika WAF menolak multipart, minta penyedia hosting meninjau aturan hanya untuk endpoint admin terkait, jangan mematikan seluruh perlindungan.

Jika permintaan API di tab Network mendapat HTTP 200 tetapi isi JSON `{"message":"Access denied by Imunify360 bot-protection..."}`, respons itu berasal dari WebShield sebelum mencapai Laravel. Pada 18 Oktober 2026, `POST /api/admin/oprec/upload-poster` dengan multipart sekitar 2,4 MB mendapat respons ini, sedangkan poster di bawah 1 MB berhasil dari akun dan jaringan yang sama. Jadi batas PHP 2 MB belum terbukti sebagai penyebab percobaan tersebut; menaikkan `upload_max_filesize` saja tidak akan menyelesaikan blokir WebShield. Frontend sekarang mengoptimalkan JPG/PNG/WebP berukuran di atas 900 KB menjadi WebP di bawah 900 KB sebelum mengirim poster OPREC, logo divisi, dan poster pengumuman. Batas pilihan berkas tetap 5 MB, tetapi berkas yang tersimpan adalah hasil kompresi. Unggah **isi** `frontend/out/` hasil build terbaru ke folder frontend publik untuk memakai perubahan ini. Uji lagi gambar asli 2–5 MB lewat browser dan pastikan respons upload berisi URL poster Laravel, bukan JSON penolakan WebShield. Untuk dukungan kiriman besar tanpa kompresi, minta penyedia hosting memeriksa log WebShield untuk IP, waktu, dan endpoint tersebut, lalu menyesuaikan aturan yang keliru hanya pada endpoint terkait; jangan menonaktifkan seluruh perlindungan. Setelah itu, ulangi tes hingga `/api/auth/me` benar-benar mengirim `data.emailVerifiedAt` dan akun dengan nilai `NULL` mendapat 403 dari `/api/user/dashboard`. Jangan menganggap status HTTP 200 dari WebShield sebagai keberhasilan API.

Pada laporan pengguna iPhone, tautan verifikasi dialihkan ke path tantangan `/z0f...?...wsidchk=...` lalu berakhir 404. Path itu berasal dari WebShield, bukan rute verifikasi Laravel (`/api/auth/email/verify/{id}/{hash}`). Untuk pemulihan sementara, minta pengguna membuka tautan asli dari email langsung di Safari, hapus data situs domain SIMANIKA pada Safari, lalu coba jaringan lain; jika iCloud Private Relay aktif, pilihan **Show IP Address** untuk situs ini dapat diuji. Jangan bagikan URL verifikasi lengkap karena berisi tanda tangan akun. Jika tantangan tetap berakhir 404, minta hosting meninjau log dan routing WebShield berdasarkan waktu serta IP pengguna; perbaikan kode Laravel tidak dapat mengganti respons yang terjadi sebelum request mencapai aplikasi.

Pada pemeriksaan 18 Oktober 2026, `/api/ping` di hosting menjawab dari Laravel, tetapi `GET /api/auth/email/resend` menjawab 404 `The route api/auth/email/resend could not be found.` Karena rute lokal adalah `POST`, respons hosting seharusnya 405 untuk metode GET bila rute sudah aktif. Periksa unggahan `backend/routes/api.php`, `backend/app/Http/Controllers/Auth/EmailVerificationController.php`, dan berkas auth pendukung dari rilis yang sama; jangan mencampur berkas rilis lama dan baru. Jalankan `php artisan route:list --path=auth/email/resend` di hosting bila terminal tersedia. Setelah unggahan, bersihkan cache rute dan konfigurasi (`php artisan optimize:clear` atau hapus berkas cache yang disebut di bawah melalui FTP) serta reset OPcache bila kode tetap lama. Periksa kembali tanpa sesi: `GET /api/auth/email/resend` menjadi 405 dan `POST` menjadi 401, bukan 404.

Pemeriksaan ulang pada hari yang sama sudah menunjukkan `GET /api/auth/email/resend` berstatus 405 dengan header `Allow: POST`; rute hosting kini aktif. Jika email belum diterima, prioritaskan cache konfigurasi mail, hasil `POST` kirim ulang dari browser, dan log SMTP. Pemeriksaan 405 ini belum membuktikan SMTP berhasil atau akun belum terverifikasi diblokir di dashboard.

Jika tautan verifikasi tetap tidak masuk setelah rute aktif, periksa `.env` privat hosting: `MAIL_MAILER=smtp`, `MAIL_HOST=smtp.gmail.com`, `MAIL_PORT=587`, `MAIL_USERNAME` dan `MAIL_FROM_ADDRESS` berisi `himanikamif@gmail.com`, serta `MAIL_PASSWORD` berisi App Password Gmail yang sah. `MAIL_MAILER=log` hanya menulis email ke log, tidak mengirim ke kotak masuk. Simpan kredensial tanpa membagikannya; periksa `storage/logs/laravel.log` untuk kesalahan SMTP, folder spam penerima, dan pembatasan koneksi SMTP keluar dari hosting. Respons 200 dari endpoint kirim ulang hanya menyatakan server memproses permintaan; penerimaan email harus diuji di kotak masuk asli.

Setelah mengubah `.env`, bersihkan cache konfigurasi (`php artisan optimize:clear` jika terminal tersedia; untuk FTP ikuti langkah file cache di bawah). Pertahankan `APP_KEY` yang sudah dipakai agar sesi, token, dan data terenkripsi tetap dapat dibaca. Akun lama yang belum punya `email_verified_at` harus masuk dan meminta email verifikasi di `/verify-email`. Akun Super Admin juga harus menyelesaikan verifikasi sebelum bisa memakai API admin; jangan menandai semua akun lama terverifikasi lewat SQL.

### Pemeriksaan sebelum membuka akses umum

1. Cadangkan database dan `storage/app` terlebih dahulu. Uji pemulihan cadangan di lingkungan terpisah.
2. Periksa `/api/ping`, `/sanctum/csrf-cookie`, lalu daftar akun uji dan selesaikan verifikasi email. Pastikan akun belum terverifikasi mendapat 403 pada `/api/user/*` dan `/api/admin/*`. Uji unggah poster pada dialog pembuatan periode dan editor OPREC, lalu lihat poster pada halaman publik.
3. Minta reset sandi untuk akun uji. Pastikan email masuk, tautan menuju domain publik, sandi lama gagal setelah reset, dan sesi lama berakhir.
4. Uji Google: berhasil masuk, menolak izin, dan akun lokal dengan email yang sama. Semua hasil harus kembali ke domain publik dan sesi berhasil dibaca oleh `/api/auth/me`.
5. Coba akses langsung endpoint admin serta berkas privat tanpa sesi. Pastikan respons 401/403 dan tidak ada berkas atau detail kesalahan server yang bocor.

### Perawatan rutin

- Setiap hari saat masa pendaftaran: cek `storage/logs`, antrean gagal bila antrean digunakan, kapasitas disk, dan keberhasilan pengiriman email. Tinjau lonjakan 401/403/429/500 tanpa menyimpan token atau sandi di catatan.
- Setiap minggu: buat cadangan database dan berkas unggahan di lokasi terpisah; periksa hasilnya dan pastikan hanya petugas yang berwenang dapat mengaksesnya.
- Setiap bulan atau saat ada peringatan keamanan: perbarui dependensi Laravel/Next.js secara terencana, jalankan tes dan build di lokal/staging, lalu unggah rilis bersama rencana rollback. Pantau masa berlaku sertifikat TLS dan kredensial email/Google.
- Saat insiden: batasi sementara pendaftaran bila perlu, simpan salinan log, putar kredensial yang terdampak, pulihkan dari cadangan yang teruji, dan periksa kembali akses admin serta sesi aktif sebelum membuka layanan.

Paket `mysql-schema-8.0.30.sql` berisi **skema kosong** dan 34 catatan migrasi. Tidak ada akun, data PostgreSQL, password, atau konfigurasi hosting di dalamnya. Paket ini telah diimpor ulang pada MySQL 8.0.30 lokal.

1. Di phpMyAdmin, pilih database MySQL hosting yang **kosong**. Pastikan nama database yang dipilih benar. Pada tab **Import**, pilih `mysql-schema-8.0.30.sql`, format SQL, lalu jalankan. Jangan impor ke database yang berisi data karena skrip membuat tabel baru.
2. Unggah kode `backend/` terbaru melalui FTP, termasuk `config/database.php`, `app/Support/`, model/controller yang berubah, seluruh berkas migration, dan `vendor/` Laravel 12 sesuai `composer.lock`. Dokumen ini dan berkas SQL tidak perlu ditempatkan di web root.
3. Di `.env` hosting, isi `DB_CONNECTION=mysql`, `DB_HOST`, `DB_PORT=3306`, `DB_DATABASE`, `DB_USERNAME`, dan `DB_PASSWORD` sesuai kredensial dari penyedia hosting. Hapus atau kosongkan `DB_URL` bila ada. Pertahankan `APP_KEY` yang sudah dipakai, dan set `APP_DEBUG=false`. Jangan unggah `.env` ke lokasi publik.
4. Jika ada `bootstrap/cache/config.php` atau `bootstrap/cache/routes-*.php` lama di hosting, simpan cadangannya lalu hapus file cache tersebut melalui FTP. Laravel akan membaca `.env` dan route terbaru pada request berikutnya. Folder `bootstrap/cache` tetap harus dapat ditulis oleh PHP. Jika penyedia hosting memakai PHP OPcache dan perubahan kode belum terlihat, minta reset OPcache melalui panel hosting.
5. Buka endpoint `/api/ping` dan halaman publik. Periksa log Laravel di `storage/logs` jika koneksi gagal. Bila tabel `migrations` berisi 34 baris, jangan jalankan migrasi awal lagi; untuk perubahan skema berikutnya, buat paket pembaruan terpisah.

## Akun Super Admin pertama

Skema sengaja tidak berisi akun. Sebelum membuka pendaftaran untuk umum, daftarkan akun resmi melalui aplikasi menggunakan alamat yang sama dengan `ADMIN_EMAIL` di `.env`, lalu di phpMyAdmin periksa baris `users` untuk alamat tersebut dan jalankan:

```sql
UPDATE users
SET role = 'super_admin'
WHERE LOWER(email) = LOWER('alamat-resmi-yang-sama-dengan-ADMIN_EMAIL');
```

Pastikan tepat satu baris berubah dan pemilik alamat tersebut menguasai password akun. Indeks unik MySQL mencegah lebih dari satu `super_admin`. Jangan memasukkan password polos atau hash buatan MySQL ke kolom `users.password`.

## Batasan integritas MySQL

MySQL hosting bersama dapat menolak pembuatan trigger karena membutuhkan hak `SUPER` saat binary logging aktif. Karena itu paket ini tidak memuat trigger PostgreSQL untuk mengunci mode pendaftaran event. Endpoint aplikasi tetap memvalidasi mode, peserta, dan enrolment; batasi perubahan langsung ke tabel `events`, `teams`, `team_members`, dan `event_registrations` lewat phpMyAdmin. Jika hosting memberi hak trigger atau `log_bin_trust_function_creators`, penguatan integritas database dapat disiapkan terpisah.
